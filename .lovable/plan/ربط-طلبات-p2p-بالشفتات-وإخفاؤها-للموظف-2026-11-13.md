# ربط طلبات P2P بالشفتات وإخفاؤها للموظف

## نتيجة الفحص
- القاعدة متاحة، وتم فحصها بقراءات فقط: `work_txn_assignments` يمنع أكثر من إسناد لنفس `ledger_id`؛ توجد 40 إسنادًا تاريخيًا لطلبات P2P.
- الدالة الحالية `work_link_p2p_atomic` تختار أحدث شفت، وترفض إعادة استخدام الشفتات المنتهية، وتضع `ended_reason='p2p_used'`. صلاحية تنفيذها محصورة في `service_role`.
- توجد 61 شفتًا لها `link_group`، و56 شفتًا معلّمة بالاستخدام. إحدى المجموعات لها طلبان؛ المجموعة وحدها لا تثبت أي الشفتات اختير لكل طلب.
- قائمة الموظف تستبعد الشفتات المستخدمة تلقائيًا. عرض P2P عند الأدمن يعتمد على الإسناد المباشر، وليس كل شفتات المجموعة.
- لا يوجد جدول إخفاء أو سجل تدقيق خاص بهذا الربط حاليًا.

## التغيير المطلوب
1. إضافة إجراء **إخفاء** لكل شفت في قائمة ربط الموظف، واختيار **المخفية** مع **إظهار** لاستعادته. الإخفاء يؤثر فقط على قائمة ربط صاحب الشفت، ولا يغير الأرشفة أو حالة الشفت أو ظهور الأدمن.
2. ربط الطلب بكل الشفتات المحددة دون اختيار أحدث شفت. الشفتات تظل متاحة بعد الربط وتقبل طلبات أخرى، ويمكن إضافة شفتات أخرى للطلب نفسه دون تكرار الرابط.
3. إظهار جميع الروابط المؤكدة لكل طلب في عرض الأدمن وتفاصيل الشفت وملخص الموظف، مع عدم مضاعفة الطلب داخل ملخص الموظف. الموظف يحصل فقط على تفاصيل روابط شفتاته.
4. الحفاظ على سجل Bybit والإسنادات القديمة و`link_group` و`ended_reason` و`archived_at` كما هي؛ لا حذف أو إعادة تسمية أو تعديل بيانات حالية.

## توافق التاريخ القديم
- قراءة الروابط الجديدة مع الإسنادات القديمة المباشرة، وإزالة التكرار حسب `(ledger_id, shift_id)`؛ لا حاجة لنقل أو تحديث صفوف الإنتاج.
- إبقاء مجموعات الربط القديمة معروضة بوصفها **مجموعة تاريخية**، لا تحويل كل أعضاء المجموعة إلى روابط مؤكدة لكل طلب. هذا يمنع اختراع روابط في المجموعة التي تحتوي طلبين.
- عدم استبعاد الشفتات بسبب علامة الاستخدام القديمة في قائمة ربط الموظف الجديدة؛ لا مسح تلك العلامات من القاعدة.
- الإسناد الأحادي القديم يبقى مرجعًا متوافقًا مع القراءات الحالية؛ أي إسناد توافق جديد، إذا احتاجته القراءات العامة، يضاف مرة واحدة فقط دون تحديث الإسنادات الموجودة أو استخدامه لحصر الروابط المتعددة.

## التفاصيل التقنية
- إعداد SQL إضافي فقط، دون تطبيقه على Supabase في هذه المهمة:
  - جدول `work_p2p_shift_links` بمفتاح فريد `(ledger_id, shift_id)`، وصاحب الشفت ووقت الربط ومن نفذه.
  - جدول `work_p2p_hidden_shifts` بمفتاح فريد `(user_id, shift_id)` وحالة الإخفاء؛ الاستعادة تحفظ التاريخ ولا تحذف الشفت.
  - سجل تدقيق إضافي للربط والإخفاء والاستعادة، يكتب في نفس المعاملة، مع قراءة الأدمن والموظف لسجلاته فقط.
  - GRANT وRLS صريحة لكل جدول: تفاصيل الموظف مقيدة بملكيته؛ الأدمن يرى الروابط كلها؛ الكتابة من الدوال المصرح بها فقط.
- استخدام دالة ربط جديدة متعددة الشفتات، وطبقة توافق للدالة القديمة بعد الاختبار؛ إبقاء التوقيع والقيود والجداول القديمة. رفض الشفتات غير المملوكة والتحقق من صفة الموظف/الأدمن، مع حفظ ذري وآمن لإعادة المحاولة.
- تحديث دوال الموقع المحمية وقائمة الربط وقراءات P2P فقط. لا تعديل حسابات Bybit أو دورة الشفت أو Gmail أو المفاتيح.
- غياب التحديث المطلوب يرجع رسالة واضحة ويمنع الحفظ؛ لا رجوع تلقائي للدالة القديمة التي تستهلك الشفتات.

## الاختبارات والتسليم
- اختبارات SQL محلية معزولة: إخفاء شفت واحد، عزل الموظفين، بقاء قراءة الأدمن، الاستعادة والتدقيق، تعدد شفتات الطلب، إعادة استخدام الشفت لطلب آخر، عدم الإخفاء التلقائي، منع الربط بغير المملوك، إعادة المحاولة والتراجع عند الفشل، وبقاء الإسنادات ومجموعات التاريخ والصف المالي دون تغيير.
- اختبار قراءات الأدمن والموظف وتوافق الإسناد القديم، وفحص القائمة على الكمبيوتر والموبايل بالقدر المتاح.
- تسليم قائمة الملفات وSQL وخطوات تطبيقه يدويًا والاختبارات ونتائجها؛ لا تنفيذ SQL إنتاجي ولا نشر أو إصدار برنامج الموظف.
- التحقق النهائي بحساب حقيقي غير متاح هنا لأن الاتصال Supabase خارجي؛ سيبقى موضحًا كخطوة للمالك بعد تطبيق SQL، وليس نتيجة اختبار مكتملة.
