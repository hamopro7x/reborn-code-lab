## Financial interpretation
Pending and completed provider purchases retain the business display «ناجحة» after confirmation; pending does not prove settlement. When an unlinked reversal exists, matching candidates show «قيد مراجعة العكس» and are held OUTSIDE finalized spend/productivity (not an arbitrary one-amount deduction). Consequently these totals are provisional and may understate expenditure until an admin resolves the event. No candidate becomes failed by guesswork. Cases with no matching candidates remain visible in the admin queue.

Admin decisions are immutable, account scoped, with raw evidence backup and auth.uid role validation. Legacy linkedReversal without trusted provenance creates a review case; no bulk flip to success. The manual-20261031 mark and the two exact existing manual-user-20261101 marks are preserved. Side-2 events remain archived; triggers reject new ledger inserts and the staff list excludes old side-2 rows without deletion. No provider purchase/refund is executed by a decision.

## Performance blocker correction (base 614e7e3280f7b4e287c7d6fcc50824323e859e94)
Before: every batch ran full-account reconciliation twice, looping all events/cards; ledger UPDATE was unconditional. Existing 11 confirmation tests passed but did not measure writes.
After: `bybit_reconcile_dirty(account, IDs)` visits changed IDs plus indexed affected events, previous/new candidates and shared-ID matches. No automatic full reconciliation exists. Ingest runs it once; ledger INSERT/UPDATE guard applies the same projection after mirroring. Archive/case/ledger updates require a real difference. Request timestamps are stripped from stored raw payload; immutable confirmed_at is set once. Fresh unchanged polls change **zero archive/case/ledger rows**, with at most one small account observation-fence update to reject stale concurrent responses (not zero total database writes). `last_observed_at` now means last material write, not every poll; the fence owns accepted no-op observation ordering.

Candidate tuple and provider JSONB GIN indexes support affected discovery; the scope is dirty rows plus their candidate neighborhood, not the whole month. Ledger repair uses stable txn_id keyset pages of 200, current cycle, and a durable per-account cursor. Count comparisons between side2-containing archive and ledger are removed. Follow-up uses account ID + cycle rather than a mutable list index. Ingest batches are limited to 500 and account locks fail fast with 55P03/retry instead of waiting behind a history scan. Existing global assignment retry remains intentionally available; its INSERT ON CONFLICT DO NOTHING does not update old assignments, but it still has bounded read/attempt overhead. This is not a measured production throughput SLA.

Guard coverage: only kinds `card`/`refund` require matching archive and positive confirmation; P2P, deposit, withdrawal, internal transfer and manual kinds return before that check. A historical orphan labelled card/refund is deliberately rejected, not grandfathered as confirmed. Existing orphan records are not deleted by installation.

## Staged rollout without disappearing historical rows
There is no safe instant grandfathering: age alone cannot prove a second API response. Use an expand → warm → enforce rollout, with no bulk confirmed_at UPDATE:
1. In a maintenance-reviewed additive stage install the columns, indexed dirty-ingest functions and cases/fence, but defer attaching the ledger projection guard and deploying the strict-read site. Build indexes separately/concurrently on the real large tables if required; the bundled transactional index creation can block writers and is **not** a zero-lock installation promise.
2. A separately approved warm-up job invokes the new ingest RPC from fresh provider reads, round-robin bounded pages with a durable cursor. Keep the old site/scheduler isolated: pause old writers during warm-up or fence them behind the new ingest path; the old binary is not automatically compatible. No financial corrections or age-only confirmation. Existing rows older than 30s may confirm on their first new successful request because their original first-seen is fixed; rows first archived now require another call >=30s later. The installation file alone does not implement this operational split.
3. Read-only readiness check for the entire effective cycle: every eligible archive row must have `confirmed_at >= created_at + interval '30 seconds'`, and matching ledger projections must carry confirmed/authoritative status. Rows no longer returned by Bybit remain unresolved and need a reviewed evidence path; **do not switch strict reads while these are needed for existing financial totals**.
4. Only after readiness, attach the guard and deploy strict reads on Fly, then verify archive/ledger/shift/spend against the same snapshot. New purchases obey the same 30-second second-call rule. If warm-up cannot reach readiness, stay on the old read version; do not pretend a zero-downtime cutover is proven.
